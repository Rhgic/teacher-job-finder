## 1. 项目目标与范围

面向**深圳地区教师求职市场**的微信小程序。核心价值：用户配置一套订阅规则后，
系统自动盯岗位、初筛、智能匹配评分、生成求职信草稿并提醒用户，用户确认后一键投递。

**核心功能**
- 岗位浏览：美团点餐式卡片列表，关键信息直接展示，可点开看完整 JD。
- 个性化配置：预设内容模板、简历文件上传管理、求职信息预填。
- 自动化筛选管道：规则硬筛 + LLM 智能匹配，命中即推送。
- 一键投递：把简历发到招聘方邮箱（**用户确认后才发送**）。

**非目标（本期不做）**：多城市扩展、招聘方端、支付。

## 3. 系统架构

```
外部数据源(教育局/招聘站)
        │ 爬虫抓取
        ▼
┌──────────────── 后端服务 (FastAPI) ────────────────┐
│  爬虫调度 → 清洗去重 → 入库                          │
│  规则过滤(第一层)  →  LLM匹配(第二层, DeepSeek)      │
│  API业务(用户/岗位/订阅/投递)                        │
│  发信服务(SMTP, 投递回执)                            │
└────────┬───────────────────────────┬───────────────┘
         │ 存储层                      │ HTTPS API
   MySQL/Redis/COS              微信小程序前端
         │                       (卡片列表/简历/模板)
         │ 发信
         ▼
   招聘方邮箱
```

**数据闭环**：外部源 → 爬虫清洗去重 → 存储 → API 推给前端（双向，前端回传配置与投递请求）
→ 用户卡片确认 → 发信服务发到招聘方邮箱并回写送达回执。LLM 匹配挂在中间，负责评分与求职信生成。

## 4. 数据模型（已实现，约定务必延续）

8 张表见 `models.py`：`users / user_profiles / resumes / templates / jobs / sub_rules / match_results / applications`。

**必须遵守的约定**
- 主键统一 `str(uuid4)`，`String(36)`。
- **查询热点列化、配置数据 JSON 化**：岗位 district/stage/subject 是独立索引列；订阅规则的多选条件用 JSON。
- **两条状态机用枚举，禁止裸字符串**，状态流转写成受控转移函数：
  - `MatchStatus`: `pending_push → pushed → confirmed / ignored`
  - `ApplicationStatus`: `pending → sent → delivered / failed / bounced`
- 岗位去重：`(source, external_id)` 联合唯一 + `content_hash` 指纹识别内容更新。
- 投递留档：写入 `applications.resume_url_snapshot`（投递当时的简历地址快照）。
- `match_results` 是 `sub_rules × jobs` 的交叉产出，是自动化管道的核心表。

## 5. 自动化匹配管道（核心模块）

```
新岗位入库(触发)
   → 第一层 规则过滤(区域/学段/学科/薪资/编制)  ──不符──▶ 归档
   → 第二层 LLM匹配(简历×JD 评分 + 隐性要求提取)
   → 按阈值排序入库 + 生成求职信草稿
   → 订阅消息推送(每日合并)
   → 用户确认 · 一键投递(关键关口)
```

**两层顺序不可反**：规则层便宜、确定、毫秒级，先把几百条砍到几十条；
只有规则命中的少量岗位才进 LLM 层，控制 DeepSeek token 成本（可差一个数量级）。
规则层参考实现已在 `seed.py:rule_matches_job`，请抽到 service 层复用。

**LLM 匹配输出必须是结构化 JSON + 可解释理由**（这是简历亮点，也让用户敢信任自动筛选）：
```json
{
  "score": 85,
  "matched_points": ["区域匹配:南山区", "学科匹配:语文", "JD要求班主任经验,简历有班主任经历"],
  "gaps": ["JD偏好3年以上教龄,候选人2年"],
  "reason": "高度匹配。学科、区域、编制均符合,且满足JD隐性要求(班主任)。",
  "cover_letter": "尊敬的XX学校招聘负责人:..."
}
```
prompt 结构：system 定义任务与输出契约（"只输出 JSON,无多余文字"）；
user 输入 = 简历摘要 + JD 全文 + 用户求职意向。解析失败要有兜底与重试。

## 5.5 简历按 JD 自动改写（定制简历）

让系统根据招聘方的岗位需求，自动把用户已有简历改写成更贴合该岗位的版本。
这是高价值 Agent 功能，但**整诚红线必须焊进设计**。

**前置条件：简历必须结构化**
- 仅有 PDF 文件无法改写。`resumes.structured_content`(JSON) 存分块内容：
  基本信息 / 教育 / 工作或实习经历 / 技能 / 自我评价。
- 来源：上传 PDF 解析一次填入，或用户手填/编辑。

**改写流程（接在匹配管道之后）**
1. 对高分命中岗位，读 `structured_content` + 岗位 JD。
2. LLM 产出：改写后的结构化简历 + **改动清单**(逐条说明改了什么)，写入 `resume_versions`(status=draft)。
3. 用户在「投递确认页」审核改动清单 → 通过则渲染为 PDF(`file_url`)、置 approved，
   并作为本次投递的简历(`applications.resume_version_id`)；不通过可弃用或回退原件。

**整诚红线（写进 LLM prompt 的硬约束）**
- **只能重组、突出、改措辞已有的真实内容**；严禁新增/拔高：不得虚构雇主、项目、
  学历、证书、年限或技能。
- JD 要求但用户不具备的能力 → 在改动清单里标记为"差距/未覆盖"，**不得编造填补**。
- 必须输出可逐条核对的改动清单；改写结果默认 draft，**人工审核通过才可用于投递**。

**关于"全自动投递"——本期不做**
带 AI 改写简历的全自动投递风险叠加（改坏 + 投错 + 群发），用户完全脱离环节难以兜底。
替代方案：**批量确认**——系统把改好的简历与求职信备好，用户一屏勾选一批、一键确认发送，
兼顾效率与最后一道人工闸门。

## 6. 分阶段实施任务（Codex 按序执行）

### 阶段 1 · FastAPI 骨架 + CRUD
- **目标**：基于已有模型起一个能跑的 API 服务，跑通"前端能拉到种子岗位"。
- **任务**：
  1. `main.py` 起 FastAPI app，挂载 `database.get_db` 依赖。
  2. Pydantic schemas（请求/响应 DTO），与 ORM 模型解耦。
  3. 路由：
     - `GET  /jobs`（分页 + 按 district/stage/subject 筛选）
     - `GET  /jobs/{id}`
     - `GET/PUT /profile`（用户配置）
     - `GET/POST/DELETE /resumes`、`/templates`
     - `GET/POST/PUT/DELETE /rules`（订阅规则）
  4. 统一异常处理 + 分页封装。
- **交付物**：可 `uvicorn main:app` 启动；Swagger 文档可访问。
- **验收**：`python seed.py` 后，`GET /jobs` 返回 12 条；按 `district=南山区` 能正确过滤。

### 阶段 2 · 自动化匹配管道（核心，重点打磨）
- **目标**：实现两层过滤，把规则命中的岗位送 DeepSeek 评分，结果写 `match_results`。
- **任务**：
  1. `services/rule_filter.py`：从 `seed.py` 抽出并完善第一层规则过滤。
  2. `services/llm_match.py`：封装 DeepSeek 调用，按第 5 节的 JSON 契约输出；含解析兜底 + 重试 + 超时。
  3. `services/pipeline.py`：编排「新岗位 → 对所有 active 规则跑规则层 → 命中的跑 LLM 层 → 写库」，幂等（同 rule×job 不重复评分，靠唯一约束）。
  4. 触发入口：先做一个 `POST /pipeline/run` 手动触发；阶段 6 再接调度自动触发。
  5. `services/resume_tailor.py`（见 5.5）：对高分岗位，基于 `structured_content` + JD 生成改写版简历 + 改动清单，写入 `resume_versions`(draft)。**严守整诚红线，禁止虚构**。PDF 渲染与人工审核放在阶段 3/5。
- **交付物**：手动触发后 `match_results` 出现带 `llm_score`/`reason`/`cover_letter` 的记录。
- **验收**：示例规则对种子数据产出合理评分与可解释理由；LLM 返回异常时管道不崩、有日志。

### 阶段 3 · 小程序前端
- **目标**：卡片列表 + 详情 + 投递交互。
- **任务**：
  1. 登录（微信 openid）、岗位卡片列表（关键信息直出，无需进详情）、详情页。
  2. 「推荐」页：展示 `match_results` 中本人命中岗位，带评分与理由。
  3. 配置页：简历上传（传 COS）、模板管理、订阅规则编辑。
  4. 卡片上「一键投递」按钮 → 弹出确认（选简历/模板/预览求职信）。
- **验收**：能浏览种子岗位、看到匹配推荐、走完投递确认流程（发送动作连阶段 5）。

### 阶段 4 · 订阅消息推送
- **目标**：命中岗位主动通知用户。
- **任务**：接微信订阅消息；**每日把命中岗位合并成一条**（如"今日 3 个新匹配"），不逐条推。
- **约束**：微信"一次订阅发一条"，前端需引导用户授权；推送频率克制。
- **验收**：产生命中后，次日推送一条聚合消息，点击进入推荐页。

### 阶段 5 · 发信服务
- **目标**：把简历发到招聘方邮箱并回写状态。
- **任务**：
  1. `services/mailer.py`：后端 SMTP / 邮件 API；**配好发信域名 SPF/DKIM 防进垃圾箱**。
  2. 投递流程：用户确认 → 写 `applications`(pending) → 发送 → 回写 sent/delivered/failed/bounced + 回执。
  3. 投递时写 `resume_url_snapshot` 留档；加发送频率限制。
- **验收**：确认投递后邮件实际送达测试邮箱，状态正确流转，失败有 error_msg。

### 阶段 6 · 爬虫（最后做）
- **目标**：把岗位来源从手动种子换成自动抓取，对齐 `Job` 字段，下游不改。
- **任务**：
  1. 优先对接官方公告源（深圳市教育局、各区教育局、深圳人才网等），遵守 robots、限速、缓存。
  2. 清洗 → 结构化到 `Job` 字段 → 去重入库（`external_id` + `content_hash`）。
  3. 接 APScheduler/Celery 定时；抓到新岗位后触发阶段 2 的 pipeline。
- **验收**：定时任务跑通，新岗位入库不重复，自动触发匹配管道。

## 6.5 UI 设计规范（清晰简洁，微信原生观感）

目标：打开即会用，零学习成本。整体白底、卡片化、留白足，像微信里那种规整的小程序。

**视觉基调**
- **一个主色**：全 app 只用一个品牌色（建议蓝色系）做主操作按钮、激活态、高亮；其余信息靠黑/灰字 + 留白拉层次，不堆颜色。
- **语义色克制**：绿色只用于正向语义（"有编制""匹配分"）；红/黄留给警告与错误，不滥用。
- **白底 + 浅灰分隔**：页面白底，列表区浅灰背景衬托白色卡片，分隔线一律 0.5px 细线。

**字号与字重（只三档两重）**
- 标题 15px / 正文 13px / 说明 12px；字重只用常规(400)与中等(500)，不用更粗。
- 全程句式简洁，标签用小圆角 pill。

**核心组件**
- **岗位卡片（美团点餐式，关键信息直出）**：一张卡片上直接展示 学校名 + 公办/民办标签、区域·学段·学科、薪资、编制/非编标签、截止日期、「一键投递」按钮。**用户不进详情页也能判断是否投递**；点卡片才进完整 JD。
- **底部 TabBar 四项**：岗位 / 推荐 / 投递 / 我的，激活态用主色。
- **推荐卡片**：在岗位卡片基础上加「匹配分 + 一句话命中理由 + 求职信草稿已生成」提示，按钮为「确认投递」。理由要让用户一眼看懂为什么推荐、敢不敢投。
- **主操作按钮统一**（一键投递 / 确认投递）用主色软底 pill；次要操作保持轻量描边或纯文字。

**交互**
- 投递必经确认弹层：选简历 / 选模板 / 预览求职信 → 确认后才发送。
- 筛选用顶部 chips（区域 / 学段 / 学科 / 编制），点开下拉，不跳页。

## 7. 必须守住的产品 / 合规红线

- **自动筛选，但绝不自动投递**：投递前必须用户人工确认。简历投错无法撤回，且涉合规。加了简历自动改写后更要守住——可用「批量确认」提效，但不做全自动投递。
- **简历改写整诚红线**：只能重组/突出/改措辞用户已有真实内容，严禁虚构经历、学历、证书、年限、技能；JD 要求但不具备的能力标记为"差距"，不得编造；每次改写产出可核对的改动清单，draft 经人工审核才可投递。
- **爬虫合规**：优先官方源，遵守 robots、限速、缓存；抓到的招聘方邮箱属个人信息，受《个人信息保护法》约束，谨慎存储与使用，尽量"索引+跳转原文"而非整段照搬。
- **上线资质**：微信"生活服务-求职/招聘"类目需企业主体的《人力资源服务许可证》，个人开发者拿不到。个人作品集可在体验版完整演示；公开上线须补齐企业主体 + 该许可证。
- **可解释性**：LLM 评分必须附结构化命中理由，不能只给数字。

## 8. 给 Codex 的执行提示

1. 从阶段 1 开始，**一次只做一个阶段**，做完产出可运行代码 + 简要说明，等 review 通过再继续。
2. 阶段 2 是项目技术亮点，LLM 匹配的 prompt 与结构化输出要重点打磨，输出务必稳定可解析。
3. 复用既有约定（uuid 主键、状态机枚举、JSON 配置列、去重指纹），不要另起一套风格。
4. 每个 service 写成可单测的纯函数 + 薄路由层，便于后续替换（如种子源 → 爬虫源）。
5. 生产建表用 Alembic 迁移，不要在生产直接 `create_all`。
