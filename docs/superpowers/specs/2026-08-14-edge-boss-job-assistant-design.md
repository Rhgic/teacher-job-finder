# Edge BOSS 求职助手设计

## 1. 目标与边界

目标是让卢文峰在 BOSS 直聘网页端按既定策略高效投递：先配置目标岗位，再核验公司与 JD 是否一致，只有通过核验的岗位才自动发送招呼语；随后对会话持续跟进，并留下完整证据和记录。

这不是“无差别海投器”。唯一的成功指标是：每天有效投递数和有效回复数提升，同时避免投到外包、培训、销售伪装技术岗、业务与 JD 不符的公司。

产品形态是 **Microsoft Edge Manifest V3 扩展**，仅支持 BOSS 网页版。使用者自行保持网页登录。扩展不规避验证码、反爬或平台限制；出现验证码、页面结构不识别、资料不足时立即暂停，等待人工处理。

## 2. 方案选择

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 纯 Edge 扩展 + 本地存储 + 可配置 API | 安装简单，无需本地服务；API Key 只适合个人本机使用 | **采用** |
| 扩展 + 本地 FastAPI 服务 | 密钥和任务调度更易管理，但安装与运行成本高 | 第一版不做 |
| 直接 fork 全自动开源项目 | 已有投递功能，但功能臃肿、逻辑不贴合个人策略，也混入绕风控做法 | 只借鉴流程，不复用 |

LLM 采用可配置的 OpenAI 兼容接口，默认 DeepSeek。公开检索采用可配置搜索 API（例如 Tavily 或 Serper）；扩展只读取搜索结果中用户可打开的公开页面。每条结论必须包含来源 URL 和摘录；没有充分来源则输出“信息不足”，不能伪造背调结论。

## 3. 用户配置

扩展的 Options 页面是唯一配置入口，配置保存到 `chrome.storage.local`。

### 固定默认画像

- 城市：深圳
- 目标岗位：AI 应用开发、Agent 开发、大模型应用、Python AI
- 公司：20–99 人 AI/软件创业公司优先
- 期望薪资：8–12K
- 核心能力：Python、FastAPI、RAG、Function Calling、MCP、Agent、Docker
- 项目证据：智能出行 Agent；教师招聘 AI 匹配与 RAG；跨境客服 Agent
- 偏好发布者：技术负责人、CTO、创始人
- 排除：外包、培训、销售伪装技术岗、驻场为主、明显不符的岗位

页面允许增删目标关键词、屏蔽词、薪资/公司规模/工作制要求、投递日上限、跟进节奏和自动化开关。个人资料、项目事实和话术模板可编辑，但系统模板不得把未证实的能力或指标写入招呼语。

## 4. 岗位核验与决策

在 BOSS 搜索结果/岗位详情页，Content Script 提取职位名、JD、薪资、地点、经验、学历、公司、发布者、活跃状态和页面链接，形成一个不可修改的“岗位快照”。

### 4.1 三层判定

1. **硬筛选**：职位/地点/薪资/学历不达标，或命中外包、培训、销售、驻场等排除规则，直接 `skip`。
2. **岗位匹配**：规则先打分，再由 LLM 解释 JD 与简历/项目的匹配点、缺口和疑点。模型只能使用提供的事实，不得补造经历。
3. **真实性背调**：用公司名 + 城市 + JD 关键词查询公开来源，并交叉比对以下四类事实：
   - 公司实际业务、官网产品、公开动态是否支持 JD 中的 AI/技术业务描述；
   - 发布者身份、同公司其他岗位、公司技术痕迹是否支持“技术负责人直招”；
   - 工作制、岗位职责、薪资、外包属性等在不同公开来源之间是否矛盾；
   - 公司是否具备持续经营和真实产品/客户迹象。

### 4.2 输出标准

| 决策 | 条件 | 后续动作 |
| --- | --- | --- |
| `apply` | 硬筛通过；匹配分 >= 80；无高风险矛盾；至少有一条可核验来源 | 进入自动投递队列 |
| `review` | 匹配分 60–79，或证据不足/存在中风险矛盾 | 标黄，等待人工一键决定 |
| `skip` | 硬筛失败、匹配分 < 60，或发现高风险矛盾 | 不发送，保留原因 |

高风险矛盾包括：JD 声称 AI 研发但公司公开业务无相关证据且岗位内容偏销售/招生；技术岗实为外包/驻场；发布者身份与“直招”明显不符；工作制或薪资在公开信息中严重冲突。

扩展在岗位卡片上显示颜色标签、总分和一句结论；点击侧边栏可看完整证据。`skip` 永不自动投递；`review` 只能人工强制投递，并须填写或选择原因；所有 `apply` 都可以在发送前从队列移除。

## 5. 自动投递与跟进

### 5.1 首次投递

通过 `apply` 的岗位，LLM 基于岗位快照、真实项目素材和公司背调结果生成 1 条 80–140 字的招呼语。话术必须包含一个 JD 匹配点和一个可验证的项目事实，不能出现泛泛的“贵司前景好”。

发送器在点击前再次验证当前页公司和职位与队列快照一致、尚未沟通、未超过每日上限。验证通过才填写并发送；随后检查页面的发送成功状态，写入投递流水。失败、重复、验证码或页面不一致均标记 `needs_attention`，不盲目重试。

### 5.2 自动跟进

Background Service Worker 使用 `chrome.alarms` 在设定的工作时间巡检 BOSS 会话页面，并由 Content Script 抓取新消息。会话状态为：`applied`、`replied`、`waiting_candidate`、`interview_pending`、`closed`。

- 可自动回复：普通确认、索取简历、询问公开项目链接、通用项目技术问答。
- 必须人工确认：约面时间、薪资、到岗、电话/微信、任何个人信息、文件发送、含糊或风险判断不足的消息。
- 对方未回复：按配置仅提醒一次跟进，默认投递后第 3 个工作日；同一岗位最多一次，不在非工作时间发送。

任何自动生成的回复先经过事实校验：只允许引用用户配置中的简历和项目素材；无可靠答案时回复“我补充确认后尽快回复”，并创建待办，而不是编造。

## 6. 界面

1. **Popup（控制台）**：今日配额、自动化总开关、暂停、待人工确认数量、近期结果。
2. **Options（配置）**：目标画像、简历事实库、模型/搜索 API、投递与跟进策略、数据导出/清除。
3. **BOSS 页面侧边栏**：当前岗位的匹配分、背调证据、矛盾、推荐动作、招呼语预览、人工覆盖按钮。
4. **会话页浮层**：新消息分类、建议回复、自动/人工状态和下一次跟进时间。
5. **本地记录页**：岗位、公司、决策、证据来源、发送内容、会话状态、时间线和 CSV/JSON 导出。

## 7. 技术架构

```text
BOSS 网页
  └─ Content Scripts: 抽取岗位/JD/聊天内容、渲染侧边栏、执行经确认的页面动作
       ⇅ chrome.runtime messages
Extension Service Worker
  ├─ Decision pipeline: 筛选 → LLM 匹配 → 公开信息核验 → 决策
  ├─ Queue & scheduler: 投递队列、日上限、告警、跟进提醒
  ├─ API clients: DeepSeek/OpenAI-compatible、Search API
  └─ Local repository: chrome.storage.local（结构化记录与缓存）
       ⇅
Popup / Options / Local record page
```

建议目录：

```text
edge-boss-job-assistant/
├── manifest.json
├── src/background/       # Service Worker、队列、告警、API 调用
├── src/content/          # BOSS DOM 适配、岗位/会话提取、页面 UI
├── src/domain/           # profile、job、company、decision、conversation 类型与规则
├── src/pages/            # popup、options、records
├── src/prompts/          # 结构化 JSON 输出提示词
├── src/storage/          # chrome.storage 封装与数据迁移
└── tests/                # 规则、解析 fixture、API mock
```

Manifest 使用 MV3，权限最小化：`storage`、`alarms`、`notifications`、`activeTab`、`scripting`；`host_permissions` 仅包含 BOSS、模型 API 和用户配置的搜索 API 域名。默认不用 `tabs` 权限；需要读取会话列表时再明确申请。

## 8. 数据与安全

- 所有岗位快照、决策、聊天记录和 API Key 均只保存在本机 Edge 配置中；提供一键导出和一键删除。
- API Key 在纯扩展模式下无法达到服务端密钥级保护，因此只适用于用户自用设备，不提供多人共享或云同步。
- 发送前记录 `job_url`、`company_name`、`job_title`、`message_hash` 和结果回执，用于避免重复沟通并允许审计。
- LLM 一律返回经 JSON Schema 校验的结构化结果；解析失败直接转人工，不执行页面动作。

## 9. 失败处理与测试

| 场景 | 行为 |
| --- | --- |
| 页面 DOM 变化或缺字段 | 显示“无法识别”，保存快照，停止该岗位操作 |
| 搜索 API/模型失败 | 使用规则分做 `review`，不自动发送 |
| 发现验证码/安全验证 | 立即暂停队列并通知用户 |
| 投递回执不明确 | 标记待核实，不重发 |
| 聊天意图置信度低 | 只通知，不自动回复 |

测试包括：硬筛与分数单测、JD/聊天 HTML fixture 解析测试、LLM Schema 与降级测试、投递去重/日上限/时间窗测试，以及 Edge 开发者模式下对真实页面的人工验收。先做 `dry-run`：完整评估和生成消息，但不点击发送；确认 20 个岗位结果正确后才打开自动投递。

## 10. 实施顺序与验收

1. 扩展骨架、Options、个人画像、岗位快照与纯规则打分。
2. 公司公开信息检索、证据化背调、`apply/review/skip` 侧边栏。
3. 招呼语生成、`dry-run` 队列、记录页与导出。
4. 发送前双重校验、限额、回执和手动暂停；完成 20 个岗位干跑验收后启用自动发送。
5. 会话解析、跟进提醒、低风险自动回复；高风险回复强制人工确认。

第一版验收标准：能正确读取 BOSS 岗位；对 20 个岗位生成可解释决策并可打开每条证据；不发生重复发送；每天不超过配置上限；任何来源不足、验证码、页面异常或高风险会话均不会自动发送。
